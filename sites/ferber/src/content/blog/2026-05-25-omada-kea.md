# Omada and Kea: Wi-Fi and DHCP as Two Boring Boxes

The firewall should not be the DHCP server. The access points should not be a pile of browser tabs. Two jobs, two systems: **Omada** for radios and the switch, **Kea** for leases.

## Omada, not UniFi

TP-Link's controller-managed stack: EAP access points, a PoE switch, SSIDs mapped to networks. Cheaper than UniFi. Less drama than Ubiquiti's release cycle. Fine for a house. I run the **software controller in Docker**, not a hardware OC200 and not their cloud. It lives on a lab VM that also runs other compose stacks. The controller is one directory, not the host's reason to exist.

```yaml
services:
  omada-controller:
    image: mbentley/omada-controller:5.15.24.19
    network_mode: host
    restart: unless-stopped
```

Pinned tag. Not `:latest`. Host mode is the sane choice — Omada wants a lot of ports. Miss one UDP port in bridge mode and discovery fails silently. Controller UI on HTTPS. Backup the `.cfg` *and* the volume before firmware.

Adoption on the same L2 is easy. Across a subnet boundary, broadcast will not cross. `set-inform` on the device, or DHCP option 138 pointing at the controller. That is the number-one "why won't it adopt" issue.

Default SSH on an unadopted AP is still `admin`/`admin` in the folklore. Change it. The controller takes over creds after adoption.

**Controller down ≠ network down.** APs and switches keep the last-pushed config. You cannot *change* anything. You should not panic-reboot the house because the Java app restarted.

## Kea, not dhcpd, not the edge box

ISC's `dhcpd` is EOL. Kea is JSON config, a control agent, a lease file you are not praying over. Mine runs on the same VM as the primary Unbound, not on the Netgate. The secondary resolver is a second box. Kea is the single DHCPv4 source and hands clients both resolvers as `domain-name-servers`.

```json
{
  "Dhcp4": {
    "interfaces-config": { "interfaces": [ "eth0" ] },
    "valid-lifetime": 86400,
    "option-data": [
      { "name": "domain-name-servers", "data": "10.0.0.12, 10.0.0.13" },
      { "name": "domain-name", "data": "lab.example.com" }
    ],
    "subnet4": [
      {
        "id": 1,
        "subnet": "10.0.0.0/24",
        "pools": [ { "pool": "10.0.0.100 - 10.0.0.200" } ],
        "option-data": [ { "name": "routers", "data": "10.0.0.1" } ]
      }
    ]
  }
}
```

`kea-dhcp4 -t` before restart. Trailing commas will ruin your evening.

Infrastructure gets **reservations outside the pool**. The Plex mini, the APs, the switch, the DNS pair — they do not float. `reservations-out-of-pool` so a reserved address cannot also be handed to a phone.

DNS is Unbound on dedicated boxes, not Kea pretending. Option 138 for Omada can live here. One DHCP server. One controller. Neither is the WAN.

## Why two boxes

Reboot the firewall to patch pfSense and the house should still get a lease and resolve names. Reboot the controller and Wi-Fi should still forward. That split is the whole post. UniFi-in-a-gateway and "just use the ISP router" both fail it.

Names in the sample are `example.com`. Real addresses stay off this page.
